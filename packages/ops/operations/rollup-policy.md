# 运营上下文分层与自动归档策略

## 启动与目的

用户只说“开始运营”时，默认执行一次完整运营流程：不启用/修改 Cron，不自动 Git Commit；采集和 Team 评审阶段只读，只有 Team=`approve`、Brand 无高风险阻断、动作参数完整且质量门禁=`pass` 后才自动执行批准的发布/互动动作。预检确认仓库/规划器、只读采集服务、受控执行 MCP、账号、输出冲突、Coordinator 与三个 Analyst 的真实模型 Turn 可用；失败时不归档、不访问平台。持续自动运营必须由用户单独确认，并额外验证 subagent allowlist、读写 MCP 边界、同名 Cron、Writer Lock、质量门禁和一次完整无写动作的流程验证；任一失败均 Fail Closed。每日 Cron 使用 Gateway command payload 运行 `scripts/run-xhs-daily-ops.sh`。Supervisor 为每次运行创建独立 Coordinator session，允许 `sessions_yield` 后由 completion events 恢复后续 Turn，并持续等待日报、报告、快照及审计全部完成；Cron 不直接把 yielded Agent Turn 当作任务完成。若 OpenClaw 将最后一个已成功子任务的 completion 留在 pending，Supervisor 可启动有界恢复 Turn；Coordinator 只能从既有 child session 取回独立原始评审，不得重派、模拟或补写。

为防止 Agent 每次分析加载长期累积的所有日报，历史信息按固定层级压缩：

```text
日报（事实与当日决策）
  → 周报（7 天内的趋势、决策和未决项）
    → 月报（4—6 个周周期的模式与目标进展）
      → 季报（3 个月的战略复盘）
```

这不是一次性迁移，也不建立单独的汇总 Cron。**每次每日运营分析开始时必须自动执行一次幂等的 Context Maintenance**，先补齐已结束周期的汇总和归档，再加载有限上下文进行当天分析。

## 目录与稳定键

```text
operations/
├── context-index.md
├── daily/YYYY-MM-DD.md
├── weekly/YYYY-Www.md
├── monthly/YYYY-MM.md
├── quarterly/YYYY-Qn.md
└── archive/
    ├── daily/YYYY/MM/YYYY-MM-DD.md
    ├── weekly/YYYY/YYYY-Www.md
    └── monthly/YYYY/YYYY-MM.md
```

- 周使用 ISO 周（周一至周日），稳定键 `YYYY-Www`。
- 月使用 `YYYY-MM`。
- 季度使用自然季度 `YYYY-Q1` 至 `YYYY-Q4`。
- 所有周期边界按 `Asia/Shanghai` 计算。

## 每次分析前自动执行

严格按顺序执行，单次只处理截至昨天已经结束的周期。先运行 `python3 packages/ops/scripts/ops-context.py maintain` 获取确定性的周期、输入清单、SHA-256 和有界上下文计划。脚本不移动文件，语义汇总仍由 Team 生成。Secret 门禁必须使用 `python3 packages/ops/scripts/ops-secret-scan.py <files...>`；禁止用 `grep xsec|cookie|token` 代替，因为字段名和“不得持久化 Token”等政策文本不是泄漏，grep 会产生误报：

1. **周汇总**：为所有已结束但尚无周报的 ISO 周生成周报；每次最多补 4 周。
2. **日报归档**：周报校验成功后，把该周对应日报移动到 `archive/daily/YYYY/MM/`。
3. **月汇总**：为所有已结束但尚无月报的月份生成月报；仅当与该月相交的 ISO 周均已有已校验周报时生成，按月覆盖日期去重；每次最多补 3 个月。新生成周报在下一次每日运行再成为月报输入。
4. **周报归档**：月报校验成功后，将结束日期落在该月且不再属于开放月份上下文的周报移动到 `archive/weekly/YYYY/`。
5. **季度汇总**：为所有已结束但尚无季报的季度生成季报；输入必须是该季度 3 份已校验月报；每次最多补 2 个季度。新生成月报在下一次每日运行再成为季报输入。
6. **月报归档**：季报校验成功后，将季度内月报移动到 `archive/monthly/YYYY/`。
7. **更新索引**：原子更新 `context-index.md`，记录当前周期、最新汇总、开放事项、待 Team 决策、门禁外待用户确认事项和缺失周期。

超过单次补齐上限时，在索引中记录 `backlog`，本次分析不递归加载全部历史；下一次每日分析继续补齐。

## 汇总原则

汇总是有损压缩，但必须保留决策可审计性：

- 聚合事实和 Delta，不复制每天的完整表格。
- 保留目标/KR 变化、Team 决策、Owner、自动放行动作、执行结果、分歧、风险、门禁外待确认事项和未解决问题。
- 区分“周期内首次值/末次值/净变化”和“求和值”；累计指标不能把每日快照相加。
- 不把 `partial`、质量门禁失败或角色缺失的日报当作可靠趋势点，必须写数据质量覆盖率。
- 不根据缺失日补零，不改变历史决策原意。
- 每份汇总列出输入文件及内容 SHA-256，便于判断是否需要重建。
- 输入变化时只重建受影响的尚未封存汇总；已封存季度若需修订，记录修订原因和版本，不静默覆盖结论。
- 汇总和归档前执行 Secret 扫描；发现敏感信息则停止归档并报告。

## 有界上下文加载规则

正常每日分析**禁止 glob 并读取全部历史日报**。只加载：

1. `goals.md`、`charter.md`、`context-index.md`；
2. 今天已存在的日报和仍未周结的当周日报，最多 7 份；
3. 最近 2 份周报（含开放周的滚动信息）；
4. 最近 2 份月报；
5. 最近 1 份季报；
6. `context-index.md` 指向的未决决策文件，最多 10 份。

只有在审计、修订或用户明确要求历史追溯时，才按文件路径定向读取 `archive/`；不得一次加载整个归档目录。

## 安全归档条件

只有同时满足以下条件才能移动源文件：

- 汇总文件已成功写入并能重新读取；
- 输入文件清单和 SHA-256 完整；
- 汇总覆盖所有可用源文件，缺失日期已明确记录；
- 没有 Secret 扫描错误；
- 移动不会覆盖已有归档文件。

失败时保留原文件，记录 `rollupStatus: partial`，继续当天只读采集，但 Team 决策必须标注上下文维护异常。

## 汇总文件最小结构

周/月/季报使用同一结构，不再维护三个空目录 README：周期与覆盖率、输入路径及 SHA-256、首末值与净变化、三角色结论、Team 决策及自动放行/执行结果、目标/KR 进展、分歧/风险/门禁外待确认事项、下一周期重点。

## 幂等性

- 汇总稳定键固定，重复运行不得重复追加段落。
- 输入哈希未变化时跳过重建。
- 同路径归档已存在且哈希相同视为成功；哈希不同则停止并报告冲突。
- `context-index.md` 是导航索引，不是事实源；可由汇总文件重新生成。
- 自动维护可以修改工作区，但不得自动 Git Commit/Push；目标文件存在人工改动或多机冲突时停止覆盖并报告。
- 多电脑场景同一时刻只允许一台机器作为运营管理文件 Writer；其他机器可只读采集或在独立分支 Review。
